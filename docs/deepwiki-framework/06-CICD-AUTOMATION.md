# 6. Automation & CI/CD Integration

## 6.1 Auto-Update on PR Merge

### Pipeline Trigger Flow

```
Developer merges PR to main
         │
         ▼
┌──────────────────────────┐
│  GitHub Webhook fires    │
│  event: push             │
│  ref: refs/heads/main    │
│  commits: [c1, c2, c3]  │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│  Ingestion Gateway       │
│                          │
│  1. Validate webhook sig │
│  2. Check idempotency    │
│  3. Normalize event      │
│  4. Enqueue              │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│  Generation Worker       │
│                          │
│  1. git fetch + diff     │
│  2. Identify changes     │
│  3. Compute impact       │
│  4. Generate wiki        │
│  5. Validate             │
│  6. Commit to wiki repo  │
│  7. Deploy               │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│  Notification            │
│                          │
│  • Slack: "Wiki updated" │
│  • PR comment (if from   │
│    a PR merge)           │
│  • Dashboard update      │
└──────────────────────────┘
```

### GitHub Actions Workflow (Embedded Mode)

For teams that want DeepWiki to run **inside their own CI pipeline** rather than as an external service:

```yaml
# .github/workflows/deepwiki.yml
name: DeepWiki Documentation Generation

on:
  push:
    branches: [main]
    paths-ignore:
      - 'docs/wiki/**'        # Don't re-trigger on wiki changes
      - '*.md'                 # Don't trigger on README changes

  workflow_dispatch:           # Manual trigger
    inputs:
      mode:
        description: 'Generation mode'
        required: true
        default: 'incremental'
        type: choice
        options:
          - incremental
          - full

concurrency:
  group: deepwiki-${{ github.ref }}
  cancel-in-progress: true     # Cancel previous run if new push arrives

jobs:
  generate-wiki:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    permissions:
      contents: write          # To push wiki changes
      pull-requests: write     # To comment on PRs

    steps:
      - name: Checkout source
        uses: actions/checkout@v4
        with:
          fetch-depth: 0       # Full history for diff analysis

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install DeepWiki CLI
        run: npm install -g @deepwiki/cli

      - name: Restore DeepWiki cache
        uses: actions/cache@v4
        with:
          path: |
            .deepwiki/cache
            .deepwiki/graph
          key: deepwiki-${{ hashFiles('deepwiki.config.yaml') }}-${{ github.sha }}
          restore-keys: |
            deepwiki-${{ hashFiles('deepwiki.config.yaml') }}-

      - name: Determine generation mode
        id: mode
        run: |
          if [ "${{ github.event_name }}" = "workflow_dispatch" ]; then
            echo "mode=${{ github.event.inputs.mode }}" >> $GITHUB_OUTPUT
          else
            # Auto-detect: if >50% of source files changed, do full
            CHANGED=$(git diff --name-only HEAD~1 HEAD -- 'src/**' | wc -l)
            TOTAL=$(find src -name '*.ts' | wc -l)
            if [ $CHANGED -gt $((TOTAL / 2)) ]; then
              echo "mode=full" >> $GITHUB_OUTPUT
            else
              echo "mode=incremental" >> $GITHUB_OUTPUT
            fi
          fi

      - name: Generate documentation
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          DEEPWIKI_COST_LIMIT: "10.00"
        run: |
          deepwiki generate \
            --mode ${{ steps.mode.outputs.mode }} \
            --base-ref HEAD~1 \
            --head-ref HEAD \
            --output docs/wiki \
            --verbose

      - name: Validate generated docs
        run: deepwiki validate --path docs/wiki --strict

      - name: Commit and push wiki changes
        run: |
          git config user.name "DeepWiki Bot"
          git config user.email "deepwiki-bot@noreply.github.com"

          git add docs/wiki/
          if git diff --staged --quiet; then
            echo "No wiki changes to commit"
          else
            git commit -m "docs(wiki): auto-update from $(git rev-parse --short HEAD)

            Generated by DeepWiki v$(deepwiki --version)
            Source commit: ${{ github.sha }}
            Mode: ${{ steps.mode.outputs.mode }}"

            git push
          fi

      - name: Comment on merged PR
        if: github.event_name == 'push'
        uses: actions/github-script@v7
        with:
          script: |
            // Find the PR that was merged
            const commits = ${{ toJSON(github.event.commits) }};
            const prNumbers = commits
              .map(c => c.message.match(/\(#(\d+)\)/)?.[1])
              .filter(Boolean);

            for (const pr of [...new Set(prNumbers)]) {
              await github.rest.issues.createComment({
                owner: context.repo.owner,
                repo: context.repo.repo,
                issue_number: parseInt(pr),
                body: '📚 **DeepWiki** documentation has been automatically updated for this change.\n\n' +
                      `[View updated documentation](${context.serverUrl}/${context.repo.owner}/${context.repo.repo}/tree/main/docs/wiki)`
              });
            }

      - name: Upload generation report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: deepwiki-report
          path: .deepwiki/reports/latest.json
          retention-days: 30
```

## 6.2 Git Hooks Strategy

### Pre-commit Hook (Optional — Documentation Lint)

```bash
#!/bin/bash
# .husky/pre-commit — runs deepwiki lint on staged docs

STAGED_DOCS=$(git diff --cached --name-only --diff-filter=ACM -- 'docs/wiki/**/*.md')

if [ -n "$STAGED_DOCS" ]; then
  echo "🔍 DeepWiki: Validating staged documentation..."

  # Ensure manually edited docs still pass schema validation
  echo "$STAGED_DOCS" | xargs npx deepwiki validate --files

  if [ $? -ne 0 ]; then
    echo "❌ DeepWiki validation failed. Fix issues before committing."
    exit 1
  fi

  echo "✅ DeepWiki validation passed."
fi
```

### Post-merge Hook (Local Development)

```bash
#!/bin/bash
# .husky/post-merge — notify about stale docs

CHANGED_SOURCE=$(git diff HEAD@{1} HEAD --name-only -- 'src/**')

if [ -n "$CHANGED_SOURCE" ]; then
  DRIFT=$(npx deepwiki drift --quiet 2>&1)
  if [ -n "$DRIFT" ]; then
    echo ""
    echo "⚠️  DeepWiki: Documentation may be out of date."
    echo "   Run 'npx deepwiki generate' to update."
    echo "   Stale sections: $DRIFT"
    echo ""
  fi
fi
```

## 6.3 Pipeline Design

### Stage-Gate Pipeline

```
┌─────────────────────────────────────────────────────────────────────┐
│                   DEEPWIKI GENERATION PIPELINE                      │
│                                                                     │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐     │
│  │  STAGE 1 │───▶│  STAGE 2 │───▶│  STAGE 3 │───▶│  STAGE 4 │     │
│  │  Analyze  │    │ Generate │    │ Validate │    │ Publish  │     │
│  └──────────┘    └──────────┘    └──────────┘    └──────────┘     │
│                                                                     │
│  Stage 1: ANALYZE (< 30s)                                          │
│  ├── Git diff computation                                          │
│  ├── File classification                                           │
│  ├── Graph update (incremental)                                    │
│  ├── Impact analysis                                               │
│  ├── Cache lookup                                                  │
│  └── Generation plan (which sections, estimated cost)              │
│      │                                                             │
│      ├── Gate: If estimated cost > budget → ABORT + notify         │
│      └── Gate: If no sections impacted → SKIP + log               │
│                                                                     │
│  Stage 2: GENERATE (30s - 5min per section)                        │
│  ├── Context assembly per section                                  │
│  ├── Claude API calls (parallelized where independent)             │
│  ├── Response parsing and markdown generation                      │
│  ├── Cross-reference resolution                                    │
│  └── Cost tracking per call                                        │
│      │                                                             │
│      ├── Gate: If cumulative cost > budget → STOP remaining + pub  │
│      └── Gate: If API errors > 3 → ABORT + notify                 │
│                                                                     │
│  Stage 3: VALIDATE (< 30s)                                        │
│  ├── Completeness check (all required sections present)            │
│  ├── Link validation (no broken internal links)                    │
│  ├── Metadata schema validation                                    │
│  ├── Quality scoring                                               │
│  └── Diff report (what changed in the wiki)                        │
│      │                                                             │
│      ├── Gate: If quality < threshold → REVIEW queue               │
│      └── Gate: If broken links > 0 → FIX or WARN                  │
│                                                                     │
│  Stage 4: PUBLISH (< 30s)                                         │
│  ├── Commit to wiki repository                                     │
│  ├── Build static site (if enabled)                                │
│  ├── Deploy to CDN / hosting                                       │
│  ├── Invalidate caches                                             │
│  ├── Send notifications                                            │
│  └── Update dashboard metrics                                      │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## 6.4 Caching Strategy

### Cache Layers

```
┌────────────────────────────────────────────────────────────────┐
│                     CACHING ARCHITECTURE                       │
│                                                                │
│  L1: IN-MEMORY (per worker process)                            │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │  • Parsed ASTs for current run                           │  │
│  │  • Token count estimates                                 │  │
│  │  • Template objects                                      │  │
│  │  TTL: Process lifetime                                   │  │
│  │  Size: ~200MB max                                        │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  L2: REDIS (shared across workers)                             │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │  • AI response cache (content-addressed)                 │  │
│  │  • Knowledge graph snapshots                             │  │
│  │  • Embedding vectors (hot set)                           │  │
│  │  TTL: 7 days (configurable)                              │  │
│  │  Size: ~2GB max per project                              │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  L3: PERSISTENT (database / object storage)                    │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │  • Full knowledge graph (Neo4j / serialized)             │  │
│  │  • Generation history and reports                        │  │
│  │  • All embeddings (pgvector)                             │  │
│  │  • Wiki content (git repo)                               │  │
│  │  TTL: Permanent (with compaction)                        │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  L4: CDN (read path only)                                      │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │  • Generated static site                                 │  │
│  │  • Rendered HTML/CSS/JS                                  │  │
│  │  • Diagram images                                        │  │
│  │  TTL: Until next generation                              │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### Cache Key Design

```typescript
// AI Response Cache
// Key: sha256(sectionType + sourceFilesHash + graphHash + templateVersion + modelId)
```

## 6.5 Rollback Handling

### Rollback Scenarios

```
Scenario 1: GENERATION FAILURE MID-RUN
┌────────────────────────────────────────────────────────┐
│ Problem: AI call fails after 5 of 10 sections generated│
│                                                        │
│ Strategy: PARTIAL PUBLISH                              │
│  1. Publish the 5 successfully generated sections      │
│  2. Keep previous versions of remaining 5 sections     │
│  3. Mark remaining sections as "stale" in metadata     │
│  4. Queue a retry for failed sections                  │
│  5. Notify: "Partial update — 5/10 sections updated"  │
└────────────────────────────────────────────────────────┘

Scenario 2: VALIDATION FAILURE
┌────────────────────────────────────────────────────────┐
│ Problem: Generated docs fail quality validation        │
│                                                        │
│ Strategy: HOLD & REVIEW                                │
│  1. Do NOT publish to production wiki                  │
│  2. Store on a staging branch                          │
│  3. Create a review request with diff                  │
│  4. Notify reviewers                                   │
│  5. Allow manual approval or re-generation             │
└────────────────────────────────────────────────────────┘

Scenario 3: POST-PUBLISH ISSUE DISCOVERED
┌────────────────────────────────────────────────────────┐
│ Problem: Published docs contain errors                 │
│                                                        │
│ Strategy: GIT REVERT                                   │
│  1. Wiki is in git — standard git revert               │
│  2. CLI command: deepwiki rollback --to <wiki-commit>  │
│  3. Redeploy previous version from git history         │
│  4. Mark generation run as "reverted" in audit log     │
│  5. Root-cause analysis on the generation              │
└────────────────────────────────────────────────────────┘

Scenario 4: BUDGET EXCEEDED MID-RUN
┌────────────────────────────────────────────────────────┐
│ Problem: Cost limit reached before all sections done   │
│                                                        │
│ Strategy: GRACEFUL STOP                                │
│  1. Stop queuing new AI calls immediately              │
│  2. Wait for in-flight calls to complete               │
│  3. Publish completed sections                         │
│  4. Log remaining sections as "deferred"               │
│  5. Alert: "Budget exhausted — N sections deferred"    │
└────────────────────────────────────────────────────────┘
```

### Rollback CLI

```bash
# List recent generation runs
deepwiki history --project hr-admin --last 10

# Roll back to a specific wiki version
deepwiki rollback --to wiki-v2.4.1-dw.35

# Roll back the last generation
deepwiki rollback --last

# Diff between current and a previous version
deepwiki diff --from wiki-v2.4.1-dw.35 --to wiki-v2.4.1-dw.37
```
